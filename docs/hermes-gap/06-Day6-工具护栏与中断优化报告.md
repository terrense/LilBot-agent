# Day 6 优化报告：工具循环护栏、协作式中断与审批状态缓存

日期：2026-11-03

状态：2026-11-04 已补齐验收，全量回归通过
范围：七天计划 Day 6（P7、P8）

## 1. 本次解决的问题

Day 6 处理三类问题：模型在工具执行失败后重复提交同一个调用、用户想停止当前回合却只能强制结束进程，以及计划审批检查反复读取和解析同一个 JSON 文件。

这三项的用户可见程度不同：中断会直接改变交互行为；工具护栏只在模型反复出错或原地打转时出现；缓存只减少重复文件读取，正常使用时应当保持审批结果不变。

## 2. 修改前后

| 场景 | 修改前 | 修改后 |
|---|---|---|
| 同一个工具调用连续失败 | Agent 只能依赖 `max_steps` 等总步数上限；没有针对同一工具名和参数的局部识别 | 第 2 次同样失败时向模型附加提示；同一工具本回合失败 3 次时提示换策略；同一调用第 5 次尝试在执行前被拦截 |
| 只读调用重复得到相同结果 | 没有无进展提示 | 第 2 次得到相同输出后附加提示；只提示，不阻断 |
| 当前回合中按 Ctrl+C | 走 Python `KeyboardInterrupt`，保存后退出当前交互流程 | 设置中断事件，在安全检查点收尾，保存后显示 `interrupted after N steps; session saved` |
| 重试退避期间请求中断 | 主线程 Ctrl+C 可以触发 KeyboardInterrupt；后台事件请求无法唤醒 `time.sleep()` | `threading.Event.wait()` 被中断事件唤醒，并统一进入保存和回合收尾 |
| 计划审批门检查 | 每次都读取并 JSON 解析 `plan_mode.json` | 缓存已解析内容；文件修改时间或大小变化时重新读取，删除文件时清掉缓存 |

“第 5 次阻断”的计数含义是：前 4 次真实执行都返回失败，第 5 次相同调用会在进入工具 handler 前收到合成失败结果。它阻止相同失败被无意义地重复执行，并要求模型改变参数或方案。

## 3. 实现细节

### 3.1 工具循环护栏（tool-call guardrails）

新增 `lilbot/core/guardrails.py`。控制器把工具名和排序后的 JSON 参数拼成规范化签名，再计算 SHA-256。参数键顺序不同但内容相同的调用会被识别为同一个调用。内部计数按回合隔离，并用锁保护，避免并行只读工具同时更新计数时发生竞争。

`Agent._run_one_call()` 在工具执行前向控制器询问是否应拦截；真实执行后再记录成功或失败。提示文字会进入工具返回内容，模型下一轮能看到；结构化 metadata 也会记录护栏类型和关联工具，便于 UI、日志或之后的分析读取。

成功调用会清除该调用的相同参数失败计数；同一工具的失败次数按整个回合累计，避免成功一次后又把后续错误当作全新问题。只读工具只有在连续两次返回内容完全相同的情况下才会出现“没有新信息”的提示。此提示不会阻止调用。

### 3.2 协作式中断（cooperative interruption）

新增 `Agent.request_interrupt()`，只设置线程事件，不在信号处理器中直接操作会话或抛出异常。Agent 在主循环、provider 流式输出分块、重试等待和工具批次边界检查事件。

收到中断后，Agent 会保存已经确认的消息。如果最近的 assistant 工具调用还没有对应结果，会补上“执行结果未知”的工具消息和恢复提示，避免恢复会话时把副作用操作盲目重放。保存沿用 Day 5 的 SQLite 增量持久化，再发出 `TurnFinished(outcome="interrupted")`。

CLI 主线程将 Ctrl+C 连接到 `request_interrupt()`；Dashboard 在 Agent 忙碌期间也把 Ctrl+C 连接到该方法。空闲时 Dashboard 原有的 Ctrl+C 退出行为仍然保留。

### 3.3 审批文件缓存

`_plan_approval_gate()` 仍然每次检查文件是否存在及其修改状态，但只在文件版本变化后读文件和解析 JSON。缓存签名使用纳秒级修改时间与文件大小；路径按绝对路径归一化。审批状态变化时会读取新内容，文件删除后会返回无审批状态并丢弃对应缓存。

该缓存不改变计划审批规则，也不应改变结果。它省掉的是重复的文件内容读取和 JSON 解析；本次没有为这项单独采集耗时基准。

## 5. 你可以怎样直观看到效果

以下命令都在项目根目录的 PowerShell 提示符中运行，不需要进入 Python 的 `>>>` 或 `>>` 交互提示符。

### A. 不调用模型，直接看护栏的确定性演示

在项目根目录粘贴这一条命令：

```powershell
.\.venv\Scripts\python.exe -B -c "from lilbot.core.guardrails import ToolCallGuardrailController; c=ToolCallGuardrailController(); a={'path':'missing.py'}; [print(i+1, ('BLOCKED: '+b.message) if (b:=c.before_call('read_file',a)) else ('FAILED: '+'; '.join(n.kind for n in c.after_call('read_file',a,ok=False,output='file not found',read_only=False)))) for i in range(5)]"
```

预期能看到：第 1 次普通失败；第 2 次带 `repeated_failure_warning`；第 3 次带 `tool_failure_warning`；第 4 次仍然失败；第 5 次显示 `BLOCKED`。这条命令只模拟控制器计数，不启动 LilBot、不调用模型、不访问 SQLite，也不会修改项目文件。

对比理解：旧行为没有这层控制器，相当于每次都会继续执行同一个失败调用，直到总步数上限或模型自己改变策略；新行为会把明确的失败提示交还给模型，并在第 5 次阻止 handler 再次运行。这是组件级演示，不等同于对完整 Agent 的自动化回归。

### B. 在 LilBot 里感受 Ctrl+C 的前后差异

下面故意把 API 地址指向本机不存在的端口，让 LilBot 进入短暂的网络重试等待。它不会访问真实模型服务。把整个代码块粘贴到项目根目录 PowerShell；LilBot 启动后输入一句简单消息，例如“给我一句简短问候”。看到黄色 `retry` 提示后，立刻按一次 Ctrl+C：

```powershell
$oldBaseUrl = $env:LILBOT_BASE_URL
$oldRetries = $env:LILBOT_MAX_RETRIES
try {
    $env:LILBOT_BASE_URL = 'http://127.0.0.1:9/v1'
    $env:LILBOT_MAX_RETRIES = '3'
    .\.venv\Scripts\python.exe -m lilbot --classic
}
finally {
    if ($null -eq $oldBaseUrl) { Remove-Item Env:LILBOT_BASE_URL -ErrorAction SilentlyContinue }
    else { $env:LILBOT_BASE_URL = $oldBaseUrl }
    if ($null -eq $oldRetries) { Remove-Item Env:LILBOT_MAX_RETRIES -ErrorAction SilentlyContinue }
    else { $env:LILBOT_MAX_RETRIES = $oldRetries }
}
```

预期先看到重试提示，按 Ctrl+C 后看到 `interrupted after 0 steps; session saved`，然后 LilBot 回到输入提示符。此时再按 Ctrl+C 退出 LilBot，PowerShell 会恢复原来的环境变量。旧行为是在活动回合中触发 `KeyboardInterrupt`，交互主循环会退出；新行为则结束当前回合并把控制权交回交互界面。

想直观看到会话仍可恢复，可在环境变量恢复后运行：

```powershell
.\.venv\Scripts\python.exe -m lilbot --classic --resume
```

它会加载最近保存的会话并显示消息数量。此处不需要自己连接 SQLite，也不要在 PowerShell 提示符中粘贴 Python 代码块。

### C. 哪些优化不容易“看见”

计划审批缓存是内部的小性能优化，正常功能结果应与修改前一致，所以不会出现新的按钮或明显界面变化。只读重复结果提示和失败调用阻断也属于异常路径保护：普通对话不一定自然触发。A 部分用同一个控制器按阈值模拟了这类情况。

## 6. 限制与验收状态

- 中断是协作式的（cooperative），不是强制杀线程。正在同步执行的工具 handler 不能被安全地从外部终止；provider 当前若阻塞在网络读取中，也要等到读取返回、超时或下一个流式分块到达后才能响应中断。
- 只读工具若并行执行，中断不会强行杀掉已经开始的同批 handler；Agent 会等待这些调用返回并保存结果，再在批次边界收尾。
- 2026-11-04 新增 17 个 Day 6 回归用例，包含护栏 7 个、中断 8 个和审批缓存 2 个，覆盖正常 Agent、CLI 和 Dashboard 入口。
- 验收复现并修复了 ToolStarted 事件之后仍执行 handler、达到 max_steps 时越过中断，以及工具别名分散护栏计数三处边界问题。
- 最终完整测试为 571 passed / 7 skipped / 9 subtests passed，0 failed、0 warnings。Day 6 的验收项已勾选。
- 审批缓存实测由每次读取解析 0.587 ms 降至 0.252 ms。真实 MiniMax 任务和完整基准记录见 Day 7 报告。
