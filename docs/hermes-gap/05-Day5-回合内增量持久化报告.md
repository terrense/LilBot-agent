# Day 5 优化报告：回合内增量持久化

> 日期：2026-11-02 · 分支 `dev/nayang` · 对应计划：[02-七天优化计划.md](02-七天优化计划.md) 的 Day 5（P6）

## 1. 结论

LilBot 原先把一轮对话保存在内存里，等回合结束后再导出 JSON。进程在工具执行中途异常退出时，已经完成的模型消息和工具结果可能全部丢失。

本次增加 SQLite WAL（Write-Ahead Logging，预写日志）会话库。每条用户消息、assistant 消息、工具调用和工具结果都会在进入内存历史时同步提交到数据库。旧 JSON 仍保留为兼容导出；恢复时优先读取 SQLite，发现旧 JSON 会话时自动迁移。

Day 5 四项验收均完成：故障注入恢复、单条写入耗时低于 2 ms、旧 JSON 恢复兼容、全量测试通过。FTS5 全文检索在计划中是可选项，本次没有引入。

## 2. 改动设计

### 2.1 SQLite 数据结构

新增 `lilbot/core/session_db.py`，数据库位于 `.lilbot/sessions.sqlite3`：

- `sessions` 保存 session id、更新时间、消息数量、usage 和 meta。
- `messages` 按 `(session_id, seq)` 保存有序消息 JSON。
- 开启 WAL 和 `synchronous=NORMAL`。每条消息仍是独立事务，提交后才继续执行后续工具。
- 一个 Agent 回合内复用同一个 SQLite 连接，但每条消息分别提交；回合结束或异常退出后关闭连接。回合外的单次读写用完即关，避免 Windows 临时目录无法删除被占用的数据库文件。

### 2.2 Agent 消息流

新增 `_append()` 和 `_replace_messages()`：

1. 新会话首次写入时，先把 system prompt 放入数据库。
2. 用户输入、assistant 最终文本、assistant tool call、每条 tool result、截断续写提示、团队通知和内部观察消息都经 `_append()`。
3. 压缩、工具结果裁剪和会话重置会改变已有历史，改用 `_replace_messages()` 原子替换 SQLite 中该会话的消息快照。
4. 回合结束时更新 usage/meta，并继续写原有 JSON 导出。数据库只更新元数据，不重复删除并重写整段消息历史。

### 2.3 旧会话和中断恢复

`SessionStore.load()` 先查 SQLite。没有数据库记录时再加载旧 JSON，并将其导入 SQLite。session 列表和“恢复最近会话”也合并数据库和 JSON 中的记录，因此只写入数据库、尚未到回合导出时的会话也能找到。

恢复时检查最近一组 assistant tool calls 是否都有对应的 `role=tool` 结果。缺失结果会补一条明确标记“执行结果未知”的合成 tool message，并追加提示：先检查当前状态，不要盲目重放有副作用的操作。这样既维持 OpenAI 兼容消息历史的配对结构，也避免把“没有持久化结果”误判成“工具肯定没执行”。

### 2.4 崩溃时序示例

假设模型一次提出 4 个工具调用，前三个完成后进程被中断：

```text
SQLite: user → assistant(tool_calls: 1,2,3,4) → result(1) → result(2) → result(3)
进程退出：没有机会写回合结束 JSON
恢复：读取上述 SQLite 消息，给 call 4 补“结果未知”，提示先检查状态
```

前三条已提交的结果可用；第四项不会被 LilBot 自动重跑。由于崩溃可能发生在工具产生副作用之后、结果提交之前，第四项只能标记未知，不能推断执行成功或失败。

## 5. 关键实现权衡与已知边界

- `synchronous=NORMAL` 在 WAL 模式下可以从应用进程崩溃中恢复已提交事务；突然断电时，最近一次事务的耐久性弱于 `FULL`。本次选择 `NORMAL` 是为了符合计划的低写入开销目标。
- Windows 会锁定打开的 SQLite 文件。把连接一直留到 Agent 对象销毁，会让短生命周期测试的临时目录无法清理；最终实现只在 `run_turn()` 生命周期内复用连接，并在 `finally` 关闭，回合外的读写用完即关。
- JSON 仍在回合结束时完整导出，兼容旧工具和人工检查；中途恢复以 SQLite 为准。
- 压缩会重写当前消息快照，后续消息再从新序号继续追加。这是历史裁剪场景的必要同步，不影响普通消息按条提交。
- FTS5 会话全文检索是后续能力，本次未做。
- 本次没有调用 MiniMax API；写入基准与测试均离线运行。

## 6. 学习要点

- WAL 把已提交事务追加到日志中；进程重启时 SQLite 会从 WAL 恢复数据。
- 增量写的核心收益是缩小故障时的丢失窗口，不是让 JSON 导出消失。
- tool call 和 tool result 是一组协议记录。副作用执行与结果落库之间无法组成一个跨工具、跨进程的原子事务，因此恢复逻辑必须承认“状态未知”。
- 性能测量要拆开首次初始化与稳态追加；否则 schema/WAL 初始化会掩盖每条消息的实际写入耗时。
