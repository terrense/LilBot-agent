## Day 1 · 基准测试脚手架 + HTTP 连接复用（P1）　✅ 已完成

**为什么先做它**：改动最小、收益最大、风险最低。实测每次请求浪费约 0.8 秒。

**Hermes 参考**：`agent/auxiliary_client.py` 第 3985–4060 行（`_client_cache`、`_client_cache_key`）

**改动**
1. 新建 `benchmarks/bench_runtime.py`，测四项：
   - 创建 Client 的耗时
   - 10 次连续请求的总耗时（用本地假 SSE 服务器，不花钱）
   - grep 耗时（给 Day 4 用）
   - token 估算误差（给 Day 3 用）
2. `llm/providers.py`：
   - `OpenAICompatibleProvider` 持有一个懒加载、线程安全的 `httpx.Client`（`limits=httpx.Limits(max_keepalive_connections=8, keepalive_expiry=60)`）
   - `complete()` 和 `complete_stream()` 都复用这个 Client
   - 增加 `close()`，CLI 退出时调用
   - 模块级缓存 `SSLContext`（certifi 只加载一次）
3. `/model` 切换模型或 base_url 时重建 Client（检查 `switch_runtime_model`）。
4. （实施中追加）流式响应在 `[DONE]` 之后读完剩余内容，否则连接不能回到连接池。

**验收**
- [x] 新增 `tests/test_http_client_reuse.py`：同一个 provider 连续调用两次，Client 是同一个对象；切换 base_url 后会重建；多线程并发调用（召回预取 + 主循环）没有问题
- [x] 全量测试不少于 417 passed（实际 425）
- [x] 基准：每次请求的固定开销从约 800 ms 降到 < 5 ms（实际 0.2 ms；10 次请求只用 1 条 TCP 连接）

**学习要点**：HTTP keep-alive、连接池、为什么 `httpx.Client` 是线程安全的、证书加载的成本。

## Day 2 · 错误分类 + 指数退避重试 + 备用模型（P2）

**Hermes 参考**：`agent/error_classifier.py`（`FailoverReason` 枚举）、`agent/retry_utils.py`（`jittered_backoff`）、`agent/conversation_loop.py` 第 917–1300 行（重试主循环）

**改动**
1. 新建 `lilbot/llm/errors.py`：`FailoverReason`（先实现 8 类：auth、rate_limit、overloaded、server_error、timeout、context_overflow、model_not_found、format_error）+ `classify(exc) -> ClassifiedError(reason, retryable, should_compress, should_fallback)`
2. 新建 `lilbot/llm/retry.py`：`jittered_backoff(attempt, base=2.0, max=60.0)`；如果响应带 `Retry-After` 头，按它的值等待
3. `providers.py`：网络错误（`httpx.ConnectError`、`ReadTimeout`）统一包装成带 `reason` 的 `ProviderError`（注意：非流式 `complete()` 目前完全没有捕获 `httpx.HTTPError`）
4. `agent.py:_stream_turn`：把现有的溢出恢复循环扩展为“分类 → 重试 / 压缩 / 切备用模型 / 放弃”。**流式请求已经输出文字之后不再重试**，避免重复输出
5. 配置项：`LILBOT_MAX_RETRIES`（默认 3）、`LILBOT_FALLBACK_MODEL`、`LILBOT_FALLBACK_BASE_URL`（可选）
6. 顺手修复：失败的回合也要先持久化已有的消息，再把异常往上抛

**验收**
- [ ] `tests/test_retry.py`：用假 provider 依次返回 429 → 503 → 成功，回合最终成功，并记录 2 次 `recovery` 事件；401 不重试；溢出走压缩路径；连续失败后切到备用模型
- [ ] 测试里把退避等待时间注入为 0，测试不变慢
- [ ] 全量测试通过

**学习要点**：可重试与不可重试错误的区别、为什么要加抖动（惊群效应）、流式请求的幂等性。

## Day 3 · 中文 token 估算 + 辅助模型路由（P3、P4）

**Hermes 参考**：`agent/model_metadata.py:estimate_messages_tokens_rough`、`agent/auxiliary_client.py` 开头 1–300 行（按任务选择模型）

**改动**
1. `core/compaction.py:estimate_tokens_text`：按字符类别分别估算。CJK 字符约 1 token/字（保守估计），ASCII 约 4 字符/token，其他字符约 2 字符/token。用 `re` 一次扫描完成，不引入 tiktoken
2. 用真实 `prompt_tokens` 校准：记录“真实值 / 估算值”的比例（指数移动平均），后续估算乘以这个比例
3. 新增辅助模型配置：`LILBOT_AUX_MODEL`、`LILBOT_AUX_BASE_URL`（默认等于主模型）。`_meta_query`（召回、抽取、session 笔记）走辅助 provider；压缩摘要先保持用主模型（因为它复用了主模型的前缀缓存），等测量后再决定
4. `/status` 显示估算值和真实值的偏差

**验收**
- [ ] `tests/test_token_estimate.py`：1,450 个中文字符估算在 1,000–1,600 之间；纯英文结果不变（现有压缩测试不能失败）
- [ ] 辅助 provider 测试：召回走辅助 provider，主循环走主 provider
- [ ] 基准：中文估算误差从约 -70% 降到 ±20% 以内

**学习要点**：BPE 分词对中文的影响、为什么 Hermes 也只做粗略估算而不用 tokenizer、主模型和辅助模型分离的成本模型。

## Day 4 · 搜索工具提速（P5）

**Hermes 参考**：`tools/file_operations.py` 第 1590–1720 行（rg 优先，回退到 grep / find）

**改动**
1. 新建 `lilbot/tools/search_backend.py`：
   - `find_rg()`：`shutil.which("rg")`，结果缓存
   - `rg_grep(pattern, base, glob, max_results, before, after, case_sensitive)`：调用 `rg --json`，解析成现有的 `matches` 结构
   - `walk_files(base, root)`：基于 `os.walk` 的 Python 回退实现，**在进入目录之前**就剪掉 `NOISY_DIRS`（原地修改 `dirnames`），并跳过二进制文件和超大文件（> 2 MB）
2. `_grep`、`glob`、`Sandbox.grep/glob`、`_iter_source_files` 统一改用 `walk_files` 或 rg
3. 可选：读取 `.gitignore` 的简单规则（只支持目录名和 `*.ext`）

**验收**
- [ ] 现有 grep / glob 测试全部通过（输出格式不变）
- [ ] 新测试：`.venv` 里的内容不会出现在结果里；没装 rg 时回退路径的结果和装了 rg 时一致
- [ ] 基准：仓库根目录 grep 从 1,739 ms 降到 < 150 ms（不装 rg 的情况下）

**学习要点**：先剪枝再遍历和先遍历再过滤的区别、ripgrep 为什么快、`os.walk` 和 `Path.rglob` 的差异。

## Day 5 · 回合内增量持久化（P6，即 WORKLOG 里的 Week 2 MVP）

**Hermes 参考**：`hermes_state.py` 开头 1–200 行（WAL、回退到 DELETE 模式、schema）

**改动**
1. 新建 `lilbot/core/session_db.py`：SQLite（`sessions`、`messages` 两张表，WAL 模式，`synchronous=NORMAL`），提供 `append_message(session_id, msg)` 和 `load(session_id)`
2. `agent.py`：每次 `messages.append(...)` 都改为经过 `_append()`，同时写入数据库。每个工具结果写完就相当于一个 checkpoint
3. 兼容：保留 JSON 导出；`--resume` 时如果数据库里有记录就优先读数据库；旧的 JSON 会话在第一次加载时迁移
4. 恢复：`resume` 时如果最后一条是没有配对 tool 结果的 `assistant(tool_calls)`，要标记为“中断的步骤”，并告诉模型“以下工具调用结果未知，不要盲目重试有副作用的操作”
5. （可选，有余力再做）建 FTS5 虚拟表，为后续的 `session_search` 做准备

**验收**
- [ ] 故障注入测试：在第 3 个工具调用之后抛出 `KeyboardInterrupt`，重新加载后能看到前 3 个工具结果
- [ ] 每条消息写入耗时 < 2 ms（基准测试）
- [ ] `--resume` 旧 JSON 会话仍然可以用
- [ ] 全量测试通过

**学习要点**：WAL 和 rollback journal 的区别、增量写和全量写的取舍、恢复时为什么“结果未知”不能直接重放（幂等性）。

## Day 6 · 工具循环护栏 + 中断 + 小优化（P7、P8）

**Hermes 参考**：`agent/tool_guardrails.py`（整个文件，475 行，纯函数，没有副作用）、`tools/interrupt.py`

**改动**
1. 新建 `lilbot/core/guardrails.py`：移植 `ToolCallGuardrailController` 的核心逻辑
   - 签名 = 工具名 + 规范化参数的 sha256
   - 相同签名失败 2 次：在结果后面追加提示；5 次：阻断，返回合成结果
   - 同一工具失败 3 次：提示换个思路
   - 只读工具连续返回相同结果（无进展）：提示
2. 接入 `agent.py:_run_one_call` 的前后
3. 中断：`Agent.request_interrupt()` 设置一个 `threading.Event`；主循环在每批工具之间和每次 provider 调用之前检查它；退避等待用 `event.wait(delay)` 代替 `time.sleep`；中断后先持久化，再 yield `TurnFinished(outcome="interrupted")`。TUI 和 CLI 把 Ctrl+C 映射到这个调用
4. `_plan_approval_gate`：按文件 mtime 缓存解析结果

**验收**
- [ ] `tests/test_guardrails.py`：假模型连续用相同参数调用一个失败的工具，第 5 次被阻断，回合在 20 步之内结束
- [ ] 中断测试：在工具执行期间触发中断，回合干净结束，并且已经持久化
- [ ] 全量测试通过

**学习要点**：为什么护栏默认只提示、不硬性阻断（Hermes 的 `hard_stop_enabled=False`）、协作式中断和强制中断的区别。
